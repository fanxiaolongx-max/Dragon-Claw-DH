## 2. 偏离与部分符合的处置

这一节写给「平台追问为什么不完全照规范」的场景。每条都写清：为什么这么做、如果要严格合规改哪里、改了有什么代价。

### 2.1 §1.2：根目录不是 ESM

**现象**：规范要求根 `package.json` 声明 `"type": "module"`，本项目没声明。

**原因**：基座启动应用时会在应用根目录放一个自己的 CommonJS 文件 `dh-identity-loader.js` 并 `--require` 预加载。根目录一旦声明 ESM，Node 会把这个文件当 ES 模块解析，报 `require is not defined in ES module scope`，应用在跑起来之前就退出（1.0.0 在基座上实测）。

**现状**：`run.js` 保持 CommonJS 只做启动自检，再 `import('./src/main.js')`；`src/package.json` 声明 `"type": "module"`，业务代码全是 ESM。`npm run check` 有两条规则锁死这个形态，防止有人「顺手统一」。

**如果平台把加载器改名 `.cjs`**：根 `package.json` 加 `"type": "module"`，`run.js` 改写成 `.mjs`（`app.json.entry` 同步），check 的两条规则对调即可。工作量约半天。

### 2.2 §9：基座不可用时 status 仍返回 ok

**现象**：规范示例在基座不可用时返回 `status: fail`，本项目恒返回 `ok`。

**原因**：底座每 10 秒探活、连续 3 次失败就重启应用。基座抖动时如果 healthz 跟着 fail，应用会被反复重启，正在跑的对话和定时任务全断。

**现状**：`src/routes/health.js` 顶层恒 `status: ok`，把基座真实状态放进 `base_api`（`ok`/`fail`）和 `data_mode`（`online`/`degraded`/`memory`）。日志和调试面板能看到降级。

**如果要严格照示例**：`healthHandler` 里把 `data.status` 改成 `baseOk ? 'ok' : 'fail'`，一行。代价是基座网络抖动会引发重启风暴，不建议。

### 2.3 §12.1：视觉没换成数字人浅色规范

**现状**：沿用主线版 Dragon Claw 的视觉体系，只通过 `static/css/dh-web-trim.css` 隐藏 Web 版没有后端支撑的入口，没有整体换肤。

**原因**：一期目标是让运营同事在浏览器里用到和桌面版一致的功能与肌肉记忆；换肤会动到 `static/` 里几百个页面的样式，收益与改动量不成比例。

**如果要换肤**：在 `dh-web-trim.css` 旁边加一层主题变量覆盖（`static/css/dh-web-theme.css`），由 `dh-runtime.js` 和 trim 一起注入，只改变量不改结构；需要平台给一份浅色规范的色板。

### 2.4 §12.2：`static/` 里仍有 `/api` 字面量

**现状**：`static/js/api.js` 按规范用 `location.pathname` 拼基址；但沿用桌面版的页面脚本里还有 `/api/...` 硬编码，运行时由 `dh-runtime.js` 拦截 `fetch`/XHR 统一加前缀，功能正常。

**风险**：如果平台对 `static/` 做**字面量扫描**（而不是运行验证），会被判不合规。基座验证清单第 10 项就是确认这一点。

**如果平台确实扫描**：写一次机械替换（把所有 `/api/` 字面量改成走 `api.js` 的 `DH_BASE`），再跑 `tests/platform-architecture.test.js` 和 `browser-ui-e2e`。属于纯体力活，不涉及逻辑。

### 2.5 §13.3：锁文件是在外网生成后改的地址

**现状**：`package-lock.json` 的 `resolved` 已全部指向内网源，但这份锁是在外网环境生成后把地址替换过来的——包名、版本、`integrity` 校验值都没变，只是下载地址换了。风险是内网源上某个版本的 tarball 与外网不完全一致时，`integrity` 校验会失败。

**收尾动作**（合规审计会问）：找一台内网机器，删掉 `node_modules` 和锁文件后 `npm install`，把新生成的 `package-lock.json` 提交；同时确认 `profiles/lite/package-lock.json` 也重生成一次。之后 `npm ci` 能跑通就说明对齐了。

## 3. 上基座后要补的验证

`§16.2` 目前是「未验证」——所有结论都来自 `devtools/real-base/`（真 MySQL 8 + 模拟网关），真实基座上还没跑过。上基座时按 `docs/基座验证清单.md` 走一遍，重点三条：

1. **门户前缀**：`/digital-human/dh/{UUID}/` 带不带末尾斜杠都能打开，静态资源不 404。
2. **读写自身 schema**：`/api/healthz` 的 `base_api=ok`，调试面板「写自身 Schema / 查自身 Schema」都成功，并记录行数上限与单条 SQL 大小上限（大字段已按 128K 字符分片，512KB 能写入即可）。
3. **越权被拒**：普通工号调 `/api/debug/*`、`/api/db-explorer/*` 应返回 403；换一个工号看不到别人的会话。

验完把结果填进清单，并把 `devtools/parity/data.mjs` 里 `§16.2` 那条的结论从「未验证」改成「符合」，再 `node devtools/parity/gen.mjs` 重新生成 md/xlsx——**不要手改生成物**。

## 5. 规范升版时怎么改

1. 改 `devtools/parity/data.mjs` 里 `SPEC` 那一段（条款、要求、结论、备注），保持条款号与平台文档一致。
2. `node devtools/parity/gen.mjs` 重新生成 `docs/对标与规划.md` 与 `.xlsx`。
3. 同步本文：新增条款补一行，偏离项补一节「原因 + 改法」。
4. 若条款可机检，在 `scripts/check.js` 加规则，并在上表登记。
5. 跑 `npm run check && npm test`。

三份东西的分工：`data.mjs` 是唯一事实来源，`对标与规划.*` 是给管理看的汇总，本文是给写代码的人看的落地说明。
